# Native platform and thread-runtime verification

Distinguish actual native execution, emulation, stand-in IR retargeting, cross object-only, and unavailable. Never relabel missing cells as passes. Preserve actual target, emitted triple and datalayout, host/CPU/OS, SDK/sysroot, linker flags and library provenance, hashes of source/compiler/object/executable, commands, stdout/stderr, exit status and timeouts. Keep per-target counts separate.

## Native Linux x86-64 and AArch64

The release runner allows both native Linux architectures. Build HCC for the actual host and ensure emitted triple and data layout match host. Use platform GCC and Clang references with -pthread, strict C11 flags and unchanged sources. On glibc with C11 threads use the system libc path: do not separately link the fallback runtime. Run all 100 cases if possible (ABI/layout cases are target-contract; independent same-platform reference disagreement must be adjudicated). Run both mixed directions per level with Clang and GCC. Use the actual target-native backend. Check `cross_target.py --run-native-linux` matches architecture and logs all other cells as object-only.

**Native AArch64 is a high-priority completion objective**: run >=100 repetitions of the 33 marked cases at O0 and O2 if resources permit, and 1,000 repetitions each of publication HCC09-036, paired fences HCC09-039, release sequence HCC09-041, SC store-buffering HCC09-042, and SPSC ring HCC09-051 at O2 (select with repeated --case arguments). Preserve every execution. QEMU can supplement but cannot replace native weak-memory evidence; clearly record if unavailable. Pinning or scheduling variation can be logged but must not alter test semantics.

## macOS Apple Silicon / Intel, Windows MinGW / MSVC

Use project's native jobs or actual hosts. The Linux runner is intentionally not presented as a cross-OS runtime adapter. Adapt build orchestration only in a separate directory, not challenge sources or expectations. Follow the project's documented threading support: its include/threads.h and lib/threads.c on non-glibc targets, compiled for the actual ABI, POSIX -pthread on macOS where applicable, Win32/kernel32 on Windows. Record who compiled the runtime (HCC versus reference), the exact header/runtime version and options, and ensure include ordering for reference builds does not accidentally route standard atomic builtins through HCC-specific headers. Use a native reference implementation of the C11 API where available; otherwise compile the same documented fallback runtime with an independently compatible reference, or explicitly label the comparison as shared-runtime. If reference header/runtime compatibility is unavailable, record a blocked reference rather than falsifying it. Do not count Linux libc tests as validation of the fallback runtime.

Prioritise HCC09-001–027 (lifecycle, recursive/timed locks, condition variables, TLS, TSS destructors and once), HCC09-036–043 (ordering and flag), HCC09-049–055 (applications), and two-TU alignment/variadic cases HCC09-068–075 and external TLS HCC09-021. Run O0/O2, including bidirectional mixed objects where both compilers agree on the actual platform ABI. In particular check recursive mutex depth, TSS destructor re-registration, thrd_exit, condition timeout with mutex reacquisition, and native TLS isolation/alignment. Build and execute all four target matrix fixtures per available target and perform mixed ABI for bitfield-return. Do not convert GNU/MinGW results to MSVC results. Apple-on-Linux stand-in with -femulated-tls is **not** native Darwin TLS evidence. Inspect object format, actual target and any IR rewriting.

## IR and dynamic analysis

Run ir_inventory.py against the actual candidate native runs; manually inspect IR and representative native assembly. Check that plain atomic accesses are seq_cst; CAS and RMW are indivisible, correct width/alignment and correct success/failure order; release/acquire and fence placement preserve publication; signal fences use compiler-only (singlethread) semantics; TLS storage follows target ABI. HCC documents lowering consume as acquire and dynamic order as seq_cst, so legal stronger order is not a wrong-code finding. A release can tolerate stronger ordering where permitted, but document performance implications. Check optimization at backend O0/O2. Pattern extraction is not proof. If using TSan/ASan, verify actual HCC IR and runtime are instrumented (e.g. inspect sanitizer calls/attributes and run a separate known-positive control), and label unsupported/inconclusive when only reference code is instrumented. Never add deliberately racy controls to gating curated tests.
