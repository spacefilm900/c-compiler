1. Import this release **unchanged**, separate from hcc's source and in-tree tests. Verify the checksum inventory (which deliberately excludes itself). Record archive hash, import commit, exact source commit, compiler binary hash, host, Rust/compiler/backend versions, and clean working tree status. Baseline for this round is `4e69525597d484ef0712ebad933a1333c0aba55a`; if a different commit is necessary, record and explain it before running. Do not repair the candidate before freezing its first-run evidence.
2. Build `hcc` with the pinned project toolchain. Execute the full standalone runner at O0 and O2 on native x86_64 Linux with the supported Clang backend. Confirm all seven strict-mode checks and the three two-TU cases in both mixed directions at each optimisation level. Preserve generated IR, commands, all outputs, statuses and logs. Run GCC and Clang references on the actual host if practical; at least verify the current Clang oracle. No tests or expected values may be silently changed.
3. Re-run the unchanged v0.6 challenge (724 cases), both optimisation levels, and the project's existing regression harness; record unit, Csmith, torture, flagship and CI results **where actually run**. Report known failures separately. Do not merge old and new challenge scores: v0.6 remains closed, v0.7 is the new extension corpus.
4. Make a frozen pre-analysis result commit or archive first. Then analyse failures, producing reduced reproducers and citing N1570 or the documented GNU/target contract. Classify each as candidate frontend rejection/acceptance, wrong code, invalid IR, link/runtime/host issue, oracle divergence, test defect, documented limit, or inconclusive timeout. Group multiple cases by root cause. Do not call a reference divergence or unsupported feature a new compiler bug without evidence.
5. Optional: run `probes/atomic-pointer-compound/test.c` separately. GCC 14 accepts and executes it; Clang 17 rejected `p += 2`. Report the candidate and current Clang results with the relevant C11 constraint (6.5.16.2p1,p3). It is not in the 65-case release denominator. No failure should block acceptance on the basis of this probe alone pending independent adjudication.
6. Return a first-run evidence package for independent review **before repairs**. Include the frozen original outputs, source/binary provenance, per-case summary at both levels, baseline regression results, reference results, all unexpected failures with minimal reproducers, and any unresolved evidence. Include exact checksums for the files in the evidence package, excluding its own checksum manifest. Include a short human-readable report.
7. After independent review, implement repairs in hcc only, with tests-first regressions and separate commits by defect family. Re-run unchanged v0.7 and v0.6 suites and existing CI; return a frozen post-fix report. Merge only after standard code review and quality gates. No compiler patches or implementation advice are supplied in this release.

The round's initial objective is correctness of the new documented features, not expansion of scope to every C11 or GCC feature. Keep the stated limitations (complex numbers, unsupported VLA parameter qualifiers/static, computed goto into VM scope, atomic size restrictions, stronger memory-order lowering, explicit nonprototype-declaration deviation, host TLS stand-in) separate. Platform-native thread runtime and deeper ABI testing are intended for round 2; do not present this Linux first round as macOS or Windows validation.
